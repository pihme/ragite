ragite

Embeddable, CPU-friendly retrieval (RAG) as a SQLite extension.

#What it is

ragite is an embeddable retrieval component for retrieval-augmented generation (RAG). It is meant to split text into chunks, compute embeddings on the CPU and find the best-matching passages with a hybrid search (vector similarity plus full-text BM25), always with a link back to the source document and position.

It will ship as a loadable SQLite extension, so any application in any language that can load SQLite extensions can use it: SQLite for RAG.

Pre-1.0, specification only. There is no code, no release and no package yet. The design lives in SPEC.md.

#Current status

Last updated 15 October 2026 · main@ac0408e

The project so far is a written design. The specification describes the planned SQLite interface, the link from every passage back to its source document, the hybrid search that combines vector similarity with keyword ranking, and three ways to supply an embedding model: built in, chosen at build time, or loaded at run time. Each requirement is numbered so later tests can point to it. The licence, contribution guide and security policy are in place. There is no release yet.

There is no code yet, so nothing can be installed, loaded or tested, and the example on this page shows the planned interface only. The default embedding model is still open and will be picked by measuring candidates on ordinary processors. The licences of the planned dependencies and models come from early research and still have to be checked against their real package data. Reranking, reading formats such as PDF, and generating answers are outside the first version. No issues are open.

#Planned interface

Planned, not implemented. This is how the interface is designed to look; none of it works yet.

SELECT load_extension('ragite');
CREATE VIRTUAL TABLE docs USING ragite(model='default');
INSERT INTO docs(text, source) VALUES ('# Installation ...', 'manual.md');
SELECT chunk, source FROM docs WHERE docs MATCH 'How do I install it?' LIMIT 5;

#Goals

One file, no server

Documents, chunks, vectors and the full-text index live in the same SQLite database, in process.

One virtual table

Write and search through one table; INSERT, UPDATE, DELETE and ROLLBACK keep everything consistent.

CPU first

Runs well on a CPU with a built-in default embedding model; a GPU is never required, and you can bring your own model.

Rust core

The core is Rust and separate from the SQLite layer, so a plain Rust library stays possible later.

Out of scope: parsing source formats (PDF, Office, scans), answer generation and evaluation. Input is plain text, Markdown, HTML or DoclingDocument JSON.

#Model variants

VariantHow
Built-in (default)Model files embedded in the extension behind a default Cargo feature; Model2Vec models via model2vec-rs, transformer models via candle
Own model at build timeA model path passed to the build; the default model switched off with --no-default-features
External model at run timeLoaded from a local path or a URL and cached locally

The model ID is stored in the database, so ragite notices when a table is opened with a different model. The default model must run well on a CPU and use a free license (MIT or Apache-2.0); it is still open and will be chosen by benchmark. No ONNX Runtime or other C++ inference library.
