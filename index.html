#What it is

ragite is an embeddable retrieval component for retrieval-augmented generation (RAG). It splits text into chunks, computes embeddings on the CPU and finds the best-matching passages with a hybrid search (vector similarity plus full-text BM25), always with a link back to the source document and position.

It ships as a loadable SQLite extension, so any application in any language that can load SQLite extensions can use it: SQLite for RAG. Documents, chunks, vectors and the full-text index live in the same database file, in process, with no server.

#Current status

Last updated 17 October 2026 · main@5f5b2ec

The SQLite extension works on Linux x86-64. A document table takes plain text, Markdown, HTML and DoclingDocument JSON; inserts, updates, deletes and rollbacks keep chunks, vectors and the full-text index consistent, and every chunk keeps its document, position and heading path. Searches on documents or chunks fuse vector similarity and keyword ranking. The built-in retrieval model runs on an ordinary processor, and functions expose it for embedding text. Continuous integration runs the unit and SQL tests, the quickstart and the user guide examples, a parity check of the model against its reference, also on macOS and Windows builds, and the tests against the optimised release build; fuzzing, mutation tests and the model benchmark run separately. The latest release is ragite/v0.3.0. Releases are cut automatically after a release pull request is merged.

The project is before its first stable version, and the interface may still change. Release binaries are published for Linux only, and the extension is large because the model weights are built in. The chunker, scoring and other presets are fixed; another model can only be chosen when building. Bare headings stay chunks of their own and can rank high for one-word queries. Four issues are open: filters and joins on a search only see the best fused candidates; the planner does not pass a limit to the search, contrary to the specification; vector functions of the bundled vector library are exposed without a requirement covering them; and the status lines in the specification and test plan are out of date.

#Quickstart

Download libragite.so from the latest release (Linux x86-64) or build it with cargo build -p ragite-sqlite --release. Start sqlite3 in the directory that holds the file:

SELECT load_extension('./libragite');
SELECT name, technical_id FROM ragite_default_model();
CREATE VIRTUAL TABLE docs USING ragite;
INSERT INTO docs(text, source, format)
VALUES ('# Installation

Run the installer and restart the application.', 'manual.md', 'text/markdown');
SELECT chunk, source, score FROM docs_chunks WHERE docs_chunks MATCH 'How do I install it?' LIMIT 5;

Pass the path without .so; SQLite adds the suffix. This block is run as a test, so it stays correct. The user guide covers formats, updates and transactions, linking results to your own tables, the embedding functions and models; its examples run in CI too.

#Interface

PartWhat it does
CREATE VIRTUAL TABLE docs USING ragiteThe Document table. INSERT, UPDATE and DELETE chunk, embed and index the text; ROLLBACK undoes all of it
docs MATCH 'question'Hybrid search, one row per Document, ranked by its best chunk
docs_chunks MATCH 'question'Hybrid search over chunks, with doc_id, source, start, end, heading_path and score
Formatstext/plain, text/markdown, text/html and DoclingDocument JSON
ragite_embed and friendsEmbed text with a table's model, list the models, show the default and a table's model

Scores come from Reciprocal Rank Fusion (k = 60) of the vector ranking and the BM25 ranking, 50 candidates from each. Chunks hold at most 512 Unicode scalars with a 64-scalar overlap.

#Model

The built-in default model is potion-retrieval-32M, a static Model2Vec model trained for retrieval (English, MIT, 512 dimensions). Its weights are embedded in the extension, so the release libragite.so is about 135 MB. A different model can be built in at build time; each table stores its model's technical id, and a build that does not contain that model refuses the table instead of mixing vectors. A model is not loaded from a path or a URL at run time. No GPU and no ONNX Runtime are needed.

The chunker, the scoring and the other presets are fixed, the same for every caller. Where they live in the code, and how to add a document type, write or change a chunker or change the fusion: docs/tinkering.md.
